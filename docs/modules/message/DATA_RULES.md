# Message Module - Data Rules

**Implementation status**: Fully implemented.
Conversation lifecycle, message send/history/delete/read and real-time WebSocket delivery are all in place.
Direct messages no longer produce activity-feed notifications.
Group conversations were removed by V50; messaging is 1-1 only.

---

## Section 1: Canonical Data

| Table | Key Columns | Notes |
|-------|-------------|-------|
| `conversations` | `id`, `created_by`, `last_message_at`, `created_at`, `updated_at`, `direct_pair_key`, `request_status`, `request_recipient_id`, `request_hidden`, `request_resolved_at` | A 1-1 conversation thread. `created_by` is SET NULL if the creator deletes their account. `direct_pair_key` is the two participants' `user_id` values in sorted order, and its unique index is what lets `createDirectConversation` reuse an existing conversation instead of creating a duplicate. `request_status` (V145, `accepted`, `pending` or `declined`) says whether the recipient has accepted the conversation; every conversation that existed before V145 is `accepted`. `request_recipient_id` is the account asked to accept, kept after acceptance as history. `request_hidden` files a pending request in the recipient's hidden requests folder. `request_resolved_at` records when the request was accepted or declined. A declined conversation has its `direct_pair_key` cleared (retired) when its recipient starts a fresh conversation with the sender, so the pair key always belongs to the live conversation. |
| `conversation_participants` | `conversation_id`, `user_id`, `is_admin`, `joined_at`, `left_at`, `last_read_at` | Membership record for each participant. `left_at IS NOT NULL` means the user has left the conversation. `is_admin` is a holdover from the removed group feature and carries no meaning on a 1-1 conversation. |
| `messages` | `id`, `conversation_id`, `sender_id`, `message_type`, `content`, `media_asset_id`, `shared_post_id`, `shared_story_id`, `reply_to_id`, `is_deleted`, `deleted_at`, `admin_removed_at` | Individual messages. Sender-owned soft-delete via `is_deleted = TRUE` + `deleted_at`, which clears `content` and is irreversible. `admin_removed_at` (V77) is the independent moderation tombstone; it preserves the payload so a restore can return it, and a message is hidden when either tombstone is set. |
| `message_reactions` | `id`, `message_id`, `user_id`, `emoji`, `reacted_at`, `admin_removed_at` | One emoji reaction per user per message (V146, `UNIQUE (message_id, user_id)`). The surrogate `id` exists because a reaction is reportable and a report's `entity_id` is one UUID. `message_id` and `user_id` cascade on delete. `reacted_at` is stamped with the database clock by the upsert and moves when the emoji changes, a deliberate exception to the rule that timestamps are not set by application statements, because a changed reaction is a new reaction. `admin_removed_at` is the reaction's own moderation tombstone, independent of the message's. |

`conversations.is_group`, `group_name`, and `group_avatar_url` were removed by V50 along with the group-conversation feature: messaging is 1-1 only now. The columns' data was copied into `archived_group_conversations` before the drop, and the group's participant and message rows were copied into `archived_group_participants` and `archived_group_messages` respectively, so no group history was destroyed by the removal.

These tables cannot be rebuilt from any other source if lost.

## Section 3: Business Rules

### A. Rules Enforced by the Database

| Rule | Enforced By |
|------|-------------|
| `messages.message_type` must be one of `'text'`, `'image'`, `'video'`, `'post_share'`, `'story_share'` | `message_type` enum |
| `conversation_participants` allows at most one row per (conversation, user) pair | Compound `PRIMARY KEY (conversation_id, user_id)` |
| `messages.shared_post_id` becomes NULL if the shared post is deleted | `ON DELETE SET NULL` |
| `messages.shared_story_id` becomes NULL if the shared story is deleted | `ON DELETE SET NULL` |
| `messages.reply_to_id` becomes NULL if the replied-to message is deleted | `ON DELETE SET NULL` |
| `conversations.created_by` becomes NULL if the creator deletes their account | `ON DELETE SET NULL` |
| Deleting a conversation cascades to participants and messages | `ON DELETE CASCADE` |
| Deleting a message or a user cascades to their `message_reactions` rows, and a user has at most one reaction per message | `ON DELETE CASCADE` on both foreign keys and `UNIQUE (message_id, user_id)` (V146) |
| Deleting a user cascades to their `conversation_participants` rows | `ON DELETE CASCADE` on FK to `users` |
| A conversation that is not `accepted` names its recipient, and `request_hidden` is never set on an `accepted` conversation | `CHECK` constraints `chk_conversations_request_recipient` and `chk_conversations_request_hidden` (V145) |

### B. Rules Enforced by Application Code

| Rule | Service / Component |
|------|---------------------|
| A user may only send messages to conversations they are an active participant of (`left_at IS NULL`) | `MessageServiceImpl.sendMessage`, `MessageServiceImpl.listHistory`, `MessageServiceImpl.markRead` |
| Every send first takes a row lock on the conversation (`ConversationRepository.lockById`), so sends into one conversation run one after another and each reads the request state and the sender's message count as the previous one left them | `MessageServiceImpl.sendMessage` |
| While a request is pending, its sender may send exactly one message and it must be text; a second message, or any other type, is refused with `MESSAGE_REQUEST_AWAITING_ACCEPTANCE` (409). A declined request refuses every send with the same code and message, so the sender cannot tell it from a pending one. The sender's message count includes tombstoned messages, so deleting the one allowed message does not buy a second | `MessageServiceImpl.sendMessage` through `InteractionPolicyService` (`MESSAGE_SEND`) |
| A send by the recipient of a request that is not yet accepted accepts it: `request_status` becomes `accepted`, `request_hidden` is cleared and `request_resolved_at` is set in the transaction that stores the message | `MessageServiceImpl.applyRequestOutcome` |
| A requester's first message that matches the recipient's Hidden Words, or that the recipient's interaction limit applies to, sets `request_hidden` on the conversation in the same transaction | `MessageServiceImpl.applyRequestOutcome` |
| A retry carrying an Idempotency-Key that already committed replays the stored response before the policy is asked, so the retry of a requester's one allowed message is not refused for having sent it; the same key with a different payload, reply target included, is `MESSAGE_IDEMPOTENCY_CONFLICT` | `MessageServiceImpl.sendMessage` |
| A new message revives the other participant's hidden membership, except that the recipient of a declined request is never revived | `MessageServiceImpl.reactivateOtherParticipants` |
| Every message response carries `replyTo`, a preview of the replied-to message resolved on the server with one batched lookup per page, limited to the conversations of the replies: the parent's id, sender, type and a text snippet (`Snippets.of`, text parents only) plus `unavailable`. A parent the sender deleted, an administrator removed or that no longer exists reports the same thing, `unavailable: true` with its id and a null sender, type and snippet, so the preview cannot tell the three apart, and an administrative restore makes the next read show the snippet again. A message that is itself tombstoned carries no preview. The same preview rides the send response, the live `message.sent.v1` payload and the conversation list's last message | `MessageMapper.toMessageResponse`, `MessageMapper.toReplyPreview`, `MessageRepository.findReplyParents`, `ReplyParents` |
| Message history is ordered by `(created_at DESC, id DESC)` and its cursor carries both values of the last message on the page, so messages sharing a `created_at` microsecond across a page boundary are neither skipped nor repeated. A cursor minted before the id joined it carries only the timestamp and resumes strictly before that instant. The page query puts `created_at <= cursor` in front of the tie-break group so it can seek on a `(conversation_id, created_at DESC, id DESC)` index; `idx_messages_conversation` is partial (`is_deleted = FALSE`) and cannot serve a history that includes tombstones, so V147 adds `idx_messages_conversation_created_id`, which `MessageHistoryKeysetRowLossIT` expects the deep-page plan to use. The newest-message preview of the conversation list breaks the same tie by `id` | `MessageRepository.findFirstByConversation`, `findByConversationBefore`, `findLastMessagePerConversation`, `MessageServiceImpl.listHistory` |
| A reaction is exactly one emoji grapheme: a ZWJ family, a skin-tone modifier, a flag, a keycap (a digit, `#` or `*` with an optional `U+FE0F`, then `U+20E3`) and a variation-selector form each count as one, while two emoji, an emoji beside text, a bare digit and plain text do not. A symbol that is also a text character, such as the heart `U+2764`, counts only with `U+FE0F`, which is how the picker emits it. The unit is the `\X` extended grapheme cluster of at most 32 characters, and the cluster must then have the UTS #51 shape and nothing else: a regional-indicator pair, a keycap, the black flag followed by lower-case tag letters and the cancel tag (a subdivision flag, the only place tag characters are accepted), or one to five Extended_Pictographic elements joined by at most four zero-width joiners, each element carrying at most one skin tone or `U+FE0F` and rendering as an emoji by default, through the selector or through the skin tone. Trailing tags, stacked combining marks, spacing marks, a dangling joiner, repeated or text variation selectors, a prepended mark, a joiner chain longer than four and a keycap mark on any other base are refused | `ReactionEmojiValidator.isSingleEmoji` |
| Reacting is `PUT /conversations/{cid}/messages/{mid}/reaction` with `{"emoji"}` and removing is `DELETE` on the same path (204, idempotent). The gates run in this order: the conversation exists, the caller is an active participant (`CONVERSATION_FORBIDDEN`, 403), no block exists between the participants in either direction (the stealth `CONVERSATION_NOT_FOUND`), the message exists in the conversation (`MESSAGE_NOT_FOUND`), the message carries neither tombstone (`MESSAGE_NOT_FOUND`), and only then is the emoji validated (`MESSAGE_REACTION_INVALID_EMOJI`, 400). The block gate therefore runs before the emoji is looked at. Reactions are not messages, so the participants of a pending message request may react and doing so changes nothing about the request | `MessageReactionServiceImpl` |
| Reacting with the emoji already set changes nothing and publishes nothing. A new reaction or a changed emoji publishes `message.reaction.changed.v1` with `{conversationId, messageId, userId, emoji, reactedAt}` and the reactor as actor, and a removal that deleted a row publishes the same event without the `emoji` key, because the outbox payload map rejects null values. A reaction an administrator removed stays removed when its owner picks another emoji and publishes nothing. The payload also carries `inboxRecipientIds`, the other active participants who may be told, decided in the reacting transaction by `MessageInboxAudience`; `MessageLiveFanoutConsumer` removes it before the event reaches the thread topic `/topic/conversations.{id}.messages` and pushes a content-free `{eventType, conversationId}` frame to each recipient's inbox topic | `MessageReactionServiceImpl`, `MessageLiveFanoutConsumer` |
| A reaction is shown only while neither it nor its message carries a tombstone. Reactions on a message its sender deleted or an administrator removed are absent from history, and an administrative restore brings back the ones hidden by the moderation tombstone, while a sender's deletion keeps them hidden for good. Removing a reaction on a tombstoned message is a no-op that keeps the row, so a restore returns the message as it was. A reaction by a user the viewer blocked, or who blocked the viewer, is absent from the viewer's history and conversation list | `MessageReactionRepository.findVisibleForMessages`, `findLatestVisiblePerConversation`, `MessageMapper.toMessageResponse` |
| `MessageResponse.reactions` lists the visible reactions of a message oldest first, loaded with one statement per history page. The conversation list row carries `lastReaction` (`userId`, `emoji`, `messageId`, `reactedAt`, `onMyMessage`) only when the newest visible reaction is newer than the conversation's `last_message_at`, and the read is bounded by `reacted_at > last_message_at` instead of scanning every message of every listed conversation. A reaction never changes `last_message_at`, the row order or the unread count, because it is not a message | `MessageServiceImpl.listHistory`, `ConversationServiceImpl.listMyConversations` |
| Moderation policy for reactions. An owner may remove a reaction and add it again, which creates a fresh visible row, so removal is not a way to keep a hidden one. Changing the emoji of a reaction an administrator removed overwrites the moderated emoji on the same row and the row stays hidden until a restore, which then shows the new value. Removal events carry the application clock for `reactedAt`, because the deleted row has no new timestamp, while a set or changed reaction carries the database `reacted_at`. Whether a removal publishes an event is decided from the row the single `DELETE ... RETURNING` statement removed, in the reacting transaction, and a reaction an administrator had already hidden publishes none | `MessageReactionServiceImpl`, `MessageReactionRepository.deleteReaction` |
| A conversation has exactly 2 participants; a duplicate request reuses the existing conversation | `ConversationServiceImpl.createDirectConversation` - the only manual path that creates a conversation, always inserting the actor plus exactly one target; it takes the pair lock first, reads the existing conversation, and reuses an accepted conversation, the sender's pending or declined one, or the pending request its recipient opens, without any permission check (a block still refuses it), reactivating the caller's membership if they had left. A recipient who declined and now writes to the sender has the old conversation retired and a new one created |
| Where a new conversation lands comes from `InteractionPolicyService` (`MESSAGE_INITIATE`): `accepted` when the recipient follows the sender, a pending request (`request_recipient_id` set) when the recipient allows everyone and does not follow the sender, a pending request with `request_hidden` when the recipient's interaction limit applies to the sender, and a refusal when the permission is `nobody` or `following` without a follow | `ConversationServiceImpl.createDirectConversation` |
| A mutual follow settles the pair: a conversation provisioned from it is `accepted`, an existing pending request is promoted to `accepted`, and a declined one is retired before a fresh `accepted` conversation is created | `DirectConversationProvisionerImpl.ensureDirectConversation` |
| The conversation list has three folders. `primary` holds accepted conversations and the caller's own outgoing requests, a declined one included because it must read as pending to its sender. `requests` holds incoming pending, non-hidden requests with at least one message, `hidden_requests` the hidden ones, and an incoming request nobody has written to appears in neither | `ConversationRepository.FOLDER_FILTER` |
| The unread total leaves out incoming requests, and `requestCount` counts incoming pending, non-hidden requests with at least one message | `MessageRepository.countTotalUnreadForUser`, `MessageRepository.countPendingRequests` |
| The recipient of a pending request that already carries a message may accept it (`request_status` becomes `accepted`, `request_hidden` is cleared, `request_resolved_at` is set), delete it (`request_status` becomes `declined`, `request_resolved_at` is set and the recipient's own `left_at` is set) or delete it and block the sender. Any other caller, a request that is not pending, and a request with no message yet all answer `CONVERSATION_NOT_FOUND`, because a request with no message is not listed to its recipient and declining it would leave a state the sender could tell from a pending one. The action takes the conversation row lock, so it cannot interleave with a send | `ConversationServiceImpl.acceptRequest`, `deleteRequest`, `blockRequester` |
| Deleting and blocking decline in one transaction with `SocialService.blockUser`: when the block fails the request stays pending. When the recipient had already blocked the sender the block is not created again and the decline still resolves the request | `ConversationServiceImpl.blockRequester` |
| A declined request is indistinguishable from a pending one for its sender. Nothing the sender reads changes: the list row and detail report `requestStatus: pending`, the recipient's participant row keeps `leftAt` empty and stays in the list row, `sendRestriction` is derived from `last_message_at`, a send is refused with the pending refusal, and the resolution event is never pushed to the thread topic | `ConversationServiceImpl.hidesDecline`, `restoreDeclinedRecipients`, `MessageLiveFanoutConsumer.consume` |
| Deleting the conversation through `DELETE /conversations/{id}` as the recipient of a pending request is the same decline as `DELETE /conversations/{id}/request`, so the sender cannot tell an ordinary delete from a decline. The sender-facing masking (participant `leftAt`, the recipient kept in the list row) applies to every unaccepted request, not only a declined one | `ConversationServiceImpl.leaveConversation`, `hidesDecline` |
| Accepting answers `CONVERSATION_NOT_FOUND` while a block exists in either direction between the two accounts, and the requests and hidden requests folders and `requestCount` leave out a request whose sender is blocked either way. Deleting and blocking stay available under a block because they only end the recipient's side | `ConversationServiceImpl.acceptRequest`, `ConversationRepository.FOLDER_FILTER`, `MessageRepository.countPendingRequests` |
| Lock order for the conversation of a pair is the advisory pair lock first, then the conversation row. Accept, delete and block, the mutual follow provisioner and the manual create path all follow it; the provisioner decides from the locked row's status rather than from the entity it read earlier, so a decline cannot be overwritten. A send takes the row lock alone | `ConversationServiceImpl.lockOpenRequest`, `DirectConversationProvisionerImpl.ensureDirectConversation`, `ConversationRepository.lockRequestStatus` |
| Stated limitation of the stealth guarantee: after a decline the recipient's later contact, or a mutual follow, retires the declined conversation and starts a fresh one, so the sender can infer the decline by noticing that a new thread replaced the old one. The replacement is deliberate (the declined thread must not be reopened for a recipient who chose to end it) and the sender never sees the decline directly | `ConversationServiceImpl.createDirectConversation`, `DirectConversationProvisionerImpl.ensureDirectConversation` |
| Accepting, explicitly or by replying, and deleting each enqueue `message.request.resolved.v1` with `{conversationId, resolution}` (`accepted`, `deleted` or `blocked`) and the recipient as actor. The only consumer is the analytics import, which stores `message_request_accept` or `message_request_delete` with `{"blocked":bool}`; it is never delivered to the sender | `ConversationServiceImpl`, `MessageServiceImpl.applyRequestOutcome`, `DomainSignalMappings` |
| A blocked user may not initiate or reply to messages with the blocker | Initiation enforced by the policy's block rule through `ConversationServiceImpl.createDirectConversation`; replies enforced by the same block rule through `MessageServiceImpl.sendMessage`, which reads the other participant whatever their `left_at` says so a peer who deleted the conversation and then blocked the sender is still found, and answers with the stealth `CONVERSATION_NOT_FOUND` |
| Message soft-delete sets `is_deleted = TRUE` and `deleted_at = NOW()`, and clears `content` to a tombstone | `MessageServiceImpl.deleteMessage` |
| Only the message sender may delete their own message | `MessageServiceImpl.deleteMessage` |
| `last_read_at` on `conversation_participants` is updated when the user reads the conversation | `MessageServiceImpl.markRead` |
| A message of type `'post_share'` must have `shared_post_id` set; `'story_share'` must have `shared_story_id` set | `MessageServiceImpl.sendMessage` payload validation |
| A message of type `'image'` or `'video'` must have `media_asset_id` set | `MessageServiceImpl.sendMessage` payload validation |
| A live WebSocket SUBSCRIBE to a conversation's topic is rejected unless the subscriber is an active participant | `MessageWebSocketAuthInterceptor` |
| V147 builds these message-module indexes `CONCURRENTLY`: `idx_conversations_request_inbox` (pending requests per recipient and folder, newest activity first), `idx_conversations_request_recipient` (the `ON DELETE SET NULL` foreign key on `request_recipient_id`), `idx_messages_conversation_created_id`, `idx_message_reactions_message` (a message's reactions in time order) and `idx_message_reactions_reacted_at` (the conversation list's latest-reaction read, pinned by `MessageReactionRepositoryIT.latestVisible_plan_usesTheReactedAtIndex`). `InteractionControlIndexesIT` asserts each exists and is valid | `V147__add_interaction_control_indexes.sql` |
| A reaction is reportable (`report_type = 'message_reaction'`, the reaction id as `entity_id`) and removable by a moderator. `admin_removed_at` on the reaction row is its own moderation tombstone, independent of the message's: a removed reaction is hidden from both participants by the same visibility predicate that hides it for a tombstoned message, its owner choosing another emoji does not clear it, and an administrative restore clears only this column. Removing or restoring a reaction publishes no `message.reaction.changed.v1`, so a client sees the change on its next read | `MessageReactionRepository.applyAdminModeration`, `AdminServiceImpl.moderateMessageReaction` |
| A live WebSocket SUBSCRIBE to `/topic/inbox.{userId}` is rejected unless the id is exactly the subscriber's own and the account is active; another user's id, a wildcard, a trailing segment and a malformed id are all refused | `MessageInboxAuthInterceptor` |
| `message.sent.v1` carries `inboxRecipientIds` and `folder` (`primary`, `requests` or `hidden_requests`), decided in the sending transaction after the request outcome is applied. The audience is the other participants who are still active, excluding the recipient of a declined request and any account blocked by or blocking the sender. `MessageLiveFanoutConsumer` pushes `{eventType, conversationId, folder}` to each recipient's inbox topic, never any message content, and strips both keys from the thread frame so a requester subscribed to the thread cannot learn that the request was filed as hidden | `MessageInboxAudience`, `MessageServiceImpl.enqueueSent`, `MessageLiveFanoutConsumer` |
| A decision about a request (`message.request.resolved.v1`) is never pushed to any inbox or thread topic, and no inbox frame is produced for the sender of a declined request, so the requester learns nothing from the live channel | `MessageLiveFanoutConsumer.consume`, `MessageInboxAudience.recipients` |

**`sender_id` cascade behavior** `[FIXED - V32]`:
`sender_id` now uses `ON DELETE SET NULL` instead of `ON DELETE CASCADE` (migration V32).
Deleting a user's account preserves their past messages for the remaining participants instead of destroying them; a null `sender_id` renders as a deleted-user placeholder in message responses.

### C. Scope Simplifications

- Messages use a hybrid soft-delete pattern: `is_deleted BOOLEAN` + `deleted_at TIMESTAMPTZ`. This differs from the `deleted_at`-only pattern used by other modules. Both fields must be set on delete.
- No end-to-end encryption in v1.
- No read receipts beyond `last_read_at` at the conversation level.
- Group chat was removed entirely (V50); messaging is 1-1 only. The `feature_flags.group_chat` table row (V18) is a leftover from before the removal - it is decorative, and there is no runtime `feature_flags` reader in this codebase.
- Real-time delivery uses a single in-process `SimpleBroker` (no distributed STOMP relay), so delivery is best-effort per instance; a client recovers any missed event through the message history endpoint on reconnect.

## Section 5: Observability

The Phase 3 query baseline panel reads `pg_stat_statements` for `messages`, `conversations` and `conversation_participants`, the module's three highest-write-volume tables, to track query-plan drift once real production traffic exists.
No application code in this module reads `pg_stat_statements`; the panel queries it directly through the read-only `luvax_monitor` role.
